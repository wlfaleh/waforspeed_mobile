# WFS-237 — [TECHNIQUE] CI de main : regrouper les fusions dans un seul run, installation des 12 bancs plus solide
Épic : E7 · Priorité : P1 Urgent · Dépend de : WFS-236 (sinon les runs annulés bloquent encore les ✅) · Origine : propositions 2 et 5 de l'agent expert ci,
validées par Smart Brain avec conditions, acceptées par l'utilisateur le 2026-11-07 (« si c'est OK pour lui, OK pour moi ») ; créé par le PO le 2026-11-07 13:11 UTC.

## Besoin (qui, quoi, pourquoi)
Chaque fusion sur `main` lance un run complet (≈ 16 jobs) dans son propre groupe de concurrence (`build-<sha>`, `build.yml` l. 30-33) : la file d'attente
s'allonge (#825 créé à 10:56, jobs démarrés à 11:49 ; #829 à #834 en file à 13:00). Et l'installation des outils du job `banc-essai` (l. 49) n'a ni délai
ni second essai, alors qu'un miroir Ubuntu bloqué a déjà figé `apt-get` jusqu'à la fin d'un job (WFS-126, job `endurance`).

## Règles de gestion
### Partie A — regrouper les fusions sur main (proposition 2)
- RG-01 : `build.yml` l. 30-33 : un **groupe de concurrence unique pour main** (par ex. `build-main`) au lieu de `build-<sha>` ; sur une branche, groupe et
  comportement inchangés (le nouvel envoi annule l'ancien).
- RG-02 : sur main, **`cancel-in-progress: false` est gardé** (un run commencé va toujours jusqu'au bout). Le run **en attente** remplacé par un plus récent
  est annulé : c'est voulu, le plus récent contient toutes les fusions ; le robot des statuts passe déjà en ✅ les tickets 🟣 dont le commit est ancêtre d'un run vert.
- RG-03 (condition de Smart Brain) : le job `résumé (commit et tickets)` (l. 241-257) liste **tous les commits et tous les tickets WFS-XX validés par le run**,
  depuis le **dernier run de main terminé** (par ex. `gh api repos/<dépôt>/compare/<sha du dernier run terminé>...<sha du run>`), et pas seulement
  `github.event.commits` du dernier envoi. Si la liste ne peut pas être lue : le résumé le dit (« liste incomplète ») et donne au moins les commits de l'envoi.
- RG-04 (condition de Smart Brain) : en cas de run **rouge** contenant plusieurs tickets, l'expert CI trouve le ticket coupable (bissection : lecture des
  journaux d'erreur, puis au besoin CI d'une branche qui reprend les commits un à un, une à la fois) et le note au journal ; l'US technique de correction
  (règle « US techniques ») vise ce ticket.

### Partie B — installation plus solide des 12 bancs (proposition 5)
- RG-05 : `build.yml` l. 49 (job `banc-essai`, étape « Outils ») : **même boucle que le job `endurance`** (l. 108-112) : `timeout 300` sur `apt-get update`
  et sur `apt-get install`, **2 essais**, avertissement `::warning::` entre les deux, échec franc après le 2e essai. Mêmes paquets qu'aujourd'hui.
- RG-06 (condition de Smart Brain) : un `timeout-minutes` au job `banc-essai` qui couvre le banc le plus long (realisme ≈ 42 min mesuré au run #825)
  + 10 min d'installation au pire : **75 min**.

### Commun
- RG-07 : **aucun** banc, seuil, test ni job affaibli, retiré ou sauté ; aucun code fusionné retiré ; les jobs de publication gardent leur comportement.
- RG-08 : `.claude/skills/expert-ci/references/pipeline.md` mis à jour (concurrence de main, résumé, boucle d'installation, délai du job `banc-essai`).
- RG-09 : US technique : CI de la branche permise (`workflow_dispatch` de `build.yml`, branche synchronisée avec `main`) autant de fois que nécessaire,
  **une à la fois**, chaque lancement noté au journal (numéro du run, ce qu'il vérifie).
