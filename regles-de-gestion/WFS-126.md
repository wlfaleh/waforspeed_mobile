# WFS-126 — Rapport de plantage sur le téléphone (Partager au lancement suivant) + banc de chauffe la nuit
Épic : E7 · Priorité : P2 Haute · Dépend de : WFS-29 ✅ (JeuActivity), WFS-114 ✅ (CI de nuit), WFS-123 ✅ (banc `chauffe`)

## Besoin (qui, quoi, pourquoi)
L'utilisateur teste lui-même l'APK sur son téléphone. Quand le jeu se ferme tout seul, il ne peut rien nous donner :
pas de logcat, pas de trace. Un jeu Android fini garde une trace du plantage et permet de l'envoyer. Objectif : au
lancement qui suit un plantage, le jeu propose « Le jeu s'est fermé — Partager le rapport » (WhatsApp, e-mail…),
pour que l'utilisateur colle le rapport dans `tache utilisateur.md` en un geste. Suite de WFS-123 (journal du
2026-11-05 14:07:21) : le banc `WFS_BANC=chauffe` (≈ 3 min) n'est lancé par aucune CI ; il passe la nuit.

## Règles de gestion
- RG-01 : **Plantage natif** : gestionnaire des signaux `SIGSEGV`, `SIGABRT`, `SIGBUS`, `SIGFPE`, `SIGILL`
  (`sigaction` avec `SA_SIGINFO | SA_ONSTACK`, pile de secours `sigaltstack` 64 Ko), installé au démarrage dans
  `android_main.cpp`. Il écrit, **avec des appels sûrs en signal seulement** (`open` / `write` / `close`, tampons
  préparés d'avance, aucun `malloc`, aucun `printf`), le fichier `plantage.txt` dans le dossier interne de l'appli :
  signal, adresse fautive, pile (≤ 32 adresses par `_Unwind_Backtrace`, chaque adresse en `libwaforspeed.so+0x…` par
  `dladdr`), version (`versionName`, `versionCode`), modèle du téléphone et version d'Android (lus au démarrage).
  Puis il rend la main au gestionnaire précédent (Android garde son tombstone et son logcat habituels).
- RG-02 : **Dernières lignes du journal** : les **200 dernières lignes** de `WFS_LOG` / `WFS_ERR` sont gardées dans un
  anneau en mémoire préparé d'avance (accroche E0 ≤ 10 lignes dans `src/core/log.h`, annoncée au Journal) et ajoutées
  à `plantage.txt` (écran en cours, mode, terrain y figurent déjà par les journaux existants).
- RG-03 : **Plantage Java** : `Thread.setDefaultUncaughtExceptionHandler` dans `JeuActivity` écrit la pile Java dans
  le même fichier, puis appelle le gestionnaire d'origine.
- RG-04 : **Au lancement suivant**, si `plantage.txt` existe : `JeuActivity` affiche une boîte Android **avant** le
  jeu (style sombre du thème de l'appli, textes en français) : « Le jeu s'est fermé la dernière fois » — boutons
  **« Partager le rapport »** (`Intent.ACTION_SEND`, texte brut, sujet « WaForSpeed — rapport de plantage vX ») et
  **« Ignorer »**. Dans les deux cas le fichier est renommé `plantage-precedent.txt` (un seul gardé) et le jeu démarre
  normalement jusqu'au menu. Aucun envoi automatique, aucun réseau, rien sans geste du joueur (confidentialité :
  `store/confidentialite.md` complété d'une phrase).
- RG-05 : **Déclencheur de test** : `adb shell am start -n com.waforspeed.game/.JeuActivity --ez wfs_plantage true`
  provoque un plantage natif volontaire 3 s après le menu (APK de test seulement, champ ignoré sinon : rien de
  déclenchable par le joueur). Sur PC, `WFS_PLANTAGE=1` fait de même dans `desktop_main.cpp` (le fichier est écrit
  dans le dossier de sortie du banc).
- RG-06 : **Test CPU** `tests/test_plantage.cpp` : anneau de 200 lignes (débordement, lignes longues coupées à 256
  caractères), mise en forme du rapport sans allocation (tampon fixe), présence des champs attendus.
- RG-07 : **CI de nuit** : le job `endurance` de `build.yml` (cron de WFS-114, et à la demande) lance aussi
  `WFS_BANC=chauffe` (≤ 4 min) et publie son journal avec les captures ; échec si `CHAUFFE rétrogradation` ou
  `CHAUFFE rétabli` manque. Les captures `chauffe-bandeau`, `chauffe-fin`, `chauffe-retabli` sont publiées en
  artefact du job (la Release d'aperçu n'est pas republiée la nuit, WFS-114). Le job de chaque fusion n'est pas allongé.
- RG-08 : **Parcours complet** (principe n° 1 du PO) : sur PC, `WFS_PLANTAGE=1` → plantage → `plantage.txt` écrit
  (pile + 200 lignes) ; relance du banc `WFS_BANC=parcours` → journal « rapport précédent trouvé » → accueil → Course
  solo → Checkpoint → Continuer → garage → Choisir → terrain → Rouler → course → fin → Menu → accueil, « 0 écart(s)
  OK ». Sur le téléphone (ligne `qa/Check.md`) : déclencheur RG-05 → l'appli se ferme → relance → boîte → « Partager »
  ouvre la feuille de partage d'Android → retour → menu → une course → Menu.

- RG-09 : **Croissance lente de la mémoire du banc d'endurance** (ajout du PO, 2026-11-05) : le job `endurance` a
  échoué une fois sur `main` après WFS-119 (+11,3 % pour un seuil de 10 %), puis +6,1 % au rejeu ; mesures
  précédentes +8,5 %, +6,4 % : marge trop mince. (a) `endurance_banc.cpp` relève, à chaque cycle, VmRSS **et** les
  compteurs du moteur déjà disponibles (tampons / textures Vulkan alloués, voitures du trafic, particules, sons actifs
  si accessibles sans toucher les zones interdites) et écrit une ligne `ENDURANCE cycle N : RSS … Mo, …` ; (b) le
  bilan donne la **pente** (Mo par cycle, régression sur les cycles 2 à 8) en plus de la croissance ; (c) nommer la
  cause au Journal (cache qui se remplit puis se stabilise, ou vraie fuite qui croît à chaque cycle). **Ne pas
  relever le seuil de 10 %** pour faire passer le job. Si la cause est dans la zone E7 (`src/platform/**`, banc),
  la corriger ici ; si elle est dans une zone interdite (`src/game/**`, `src/render/**`, `src/audio/**`…),
  **ne pas la corriger** : la décrire au Journal (fichier, fonction, Mo par cycle) et le PO crée le ticket de
  correction dans l'épic concernée. Critère : 3 lancements du job `endurance` (à la demande) sous 10 %, avec la
  pente publiée ; ou cause nommée hors zone et ticket demandé au PO.
