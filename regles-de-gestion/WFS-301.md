# WFS-301 — [TECHNIQUE] Cartes préparées (1/4) : fichier de carte prêt à charger, préparé sur le téléphone, Ville et Corniche, repli sur la construction actuelle
Épic : E0 (point d'extension) + E4 (exception PO : `lots_decor.*`, sérialisation seule) · Priorité : P2 Haute · Dépend de : WFS-268 fusionné (réouverture finie), WFS-269 fusionné

## Besoin (qui, quoi, pourquoi)
L'utilisateur (2026-11-08, via smart-brainstorming) : comme Call of Duty, FIFA ou Asphalt, les cartes doivent être **déjà prêtes sur le téléphone**
et ne plus être reconstruites à chaque lancement de course. Aujourd'hui chaque carte est construite par le code au chargement à partir de graines
(`src/world/ville.cpp`, `src/world/archi_carte.cpp` : `poser(... graine)`, `Mulberry32`), puis regroupée (WFS-268) et éclairée (WFS-269).
Ce ticket crée le **fichier de carte préparée** et sa lecture, avec le contenu de WFS-268 (décor fixe regroupé) pour Ville et Corniche.

## Décisions du PO (cadrage) — revues le 2026-11-08 sur décision de l'utilisateur
- **Préparation sur le téléphone, au premier lancement après l'installation, pas dans la CI ni dans l'APK** (décision de l'utilisateur,
  2026-11-08, via smart-brainstorming : « préparation direct, on l'appelle installation des packaging comme les autres applications »).
  L'APK ne grossit pas ; les fichiers sont écrits dans le **stockage interne de l'application** (effacés à la désinstallation).
  L'écran « Installation des paquets » est le ticket WFS-302 ; ce ticket fournit le format, la préparation et la lecture.
- **Le code de préparation est le code de construction actuel** (appelé tel quel, puis écrit dans le fichier) ; `wfs_bench` en mode
  `WFS_BANC=cuisson` sert seulement aux tests sur PC (déterminisme, captures). Rien n'est retiré : la construction actuelle reste le repli.
- Ce qui dépend de l'appareil (pipelines) reste dans le cache de WFS-262.

## Règles de gestion
- RG-01 : un fichier par carte, `<stockage interne>/paquets/<carte>.wfcarte` (Android : `internalDataPath` ; PC : `build/paquets/` ; jamais commité,
  jamais dans l'APK). En-tête : magie `WFSC`,
  version du format (entier, +1 à chaque changement du format), **empreinte de génération** (voir RG-02), taille et somme de contrôle (CRC-32 ou
  xxHash, au choix du développeur, noté au journal) de chaque bloc. Blocs nommés (au moins `decor_regroupe`), pour que WFS-303 ajoute ses blocs
  sans changer la lecture des anciens.
- RG-02 : empreinte de génération = hachage de : graine de la carte, constante `VERSION_GENERATION_CARTE` (à incrémenter par tout ticket qui change
  le résultat de `ville.cpp`, `archi_carte.cpp`, `lots_decor.*` ou de la carte), et **toutes les valeurs de `configgame.json` lues par la
  construction de la carte** (liste écrite dans le code, à côté de la constante). Le jeu recalcule l'empreinte au chargement.
- RG-03 : au chargement, le jeu lit le fichier dans le stockage interne et l'utilise **seulement**
  si magie, version, empreinte et sommes sont justes ; sinon **repli** sur la construction actuelle, et une ligne au journal du jeu dit pourquoi
  (« absent », « version », « empreinte », « somme »). Aucun plantage, aucun écran différent.
- RG-04 : **même carte** : l'image avec carte préparée et l'image avec construction actuelle sont identiques (différence ≤ 1 % des pixels sur les
  captures du banc, mêmes 4 vues que WFS-268 : départ, rue, carrefour, Corniche). Même nombre de dessins et d'objets.
- RG-05 : **déterminisme** : deux préparations de suite donnent des fichiers identiques octet par octet (aucune adresse mémoire, heure ou ordre de
  table de hachage dans le fichier) ; test CPU qui le vérifie.
- RG-06 : mesures, au journal : temps de chargement de la carte sur PC (construction actuelle / carte préparée, médiane de 5), **durée de
  préparation** de chaque carte et **place prise** par chaque fichier. Le budget de 25 Mo dans l'APK est **sans objet** (décision de l'utilisateur
  du 2026-11-08) ; le budget porte sur la place sur le téléphone et la durée d'installation (WFS-302).
- RG-06 bis : écriture sûre : le fichier est écrit sous un nom temporaire, relu et vérifié (sommes), puis renommé ; un fichier à moitié écrit
  n'est jamais lu. Fonction `preparer_carte(carte, progression)` qui rend une progression de 0 à 1 et peut reprendre (utilisée par WFS-302).
- RG-06 ter : tant que WFS-302 n'est pas fusionné : si le fichier manque, le jeu construit la carte comme aujourd'hui puis écrit le fichier
  (la course suivante sur cette carte le lit).
- RG-07 : mémoire : la règle générale (≤ 1 Go par carte au chargement) reste ; la lecture ne garde pas deux copies du décor (le tampon lu est libéré
  après envoi à la carte graphique) ; la préparation non plus (écriture par blocs).
- RG-08 : test de parcours complet : accueil → choix Ville → course → retour → Corniche → course → retour, avec fichier présent puis fichier absent
  (repli) ; preuve au journal.
