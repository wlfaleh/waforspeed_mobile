## Constat technique (lead dev, 2026-11-08, lecture seule)
- Une carte est aujourd'hui du code. **Décor et rendu** (maillages `Vertex` de 36 octets, textures KTX2) peuvent aller dans le paquet ;
  **tracé** (`Track::build`, `track.cpp:33`), **chocs** (`chocs_decor.h`), trafic, piétons et feux restent dans le code : juste pour la Ville
  actuelle (même tracé). Une future carte au tracé différent demandera tracé + chocs dans le paquet : à prévoir dans le format (RG-01).
- Toute lecture passe par `readAsset()` / `AAssetManager` (`android_main.cpp:37-45`, `ktx2_charger.cpp:14`, `model_loader.cpp:95`).
- Ville préparée ≈ 162 Mo en mémoire graphique, ≈ 900 000 triangles (journal, WFS-268) ; textures en 3 variantes (ASTC / ETC2 / RGBA8) ;
  le lecteur KTX2 n'accepte pas la supercompression ; pas de SHA-256 ni de compression dans `src/` aujourd'hui.

## Règles de gestion
- RG-01 : un fichier par carte **et par format de texture** : `<carte>_<astc|etc2|rgba8>.wfcarte`, rangé dans `<stockage interne>/paquets/`
  (Android : `internalDataPath` ; PC : `build/paquets/`) ; jamais commité, jamais dans l'APK. En-tête : magie `WFSC`, **version du format** (lue en
  premier ; un jeu plus ancien refuse proprement un format plus récent), nom et version de la carte, format de texture, **empreinte** (RG-02),
  taille et CRC-32 de chaque bloc. Blocs nommés : `decor_regroupe`, `maillages`, `textures` (KTX2 **sans** supercompression) ; noms **réservés**
  `trace` et `chocs` (vides pour la Ville actuelle, pour une future carte au tracé différent) ; un bloc inconnu est ignoré.
- RG-02 : empreinte = hachage de la graine, de `VERSION_GENERATION_CARTE` et des valeurs de `configgame.json` lues par la construction (liste
  écrite dans le code). Le jeu connaît l'empreinte qu'il attend.
- RG-03 : **2e source de lecture** (accroche E0) : `readAsset()` cherche d'abord dans le paquet vérifié de la carte (stockage interne), puis dans
  l'APK ; même fonction, aucun appelant changé (`ktx2_charger.cpp`, `model_loader.cpp` inchangés). Le C++ ne lit **que des fichiers finis**
  (jamais un `.part`).
- RG-04 : **même carte** : la Ville actuelle cuite puis lue donne la même image que construite (≤ 1 % des pixels, 4 vues de WFS-268), mêmes dessins
  et objets ; deux cuissons identiques octet par octet (test CPU).
- RG-05 : `verifier_carte(carte)` : vérification légère (en-tête, version, format de texture, empreinte, tailles, CRC) < 200 ms sur le téléphone ;
  la somme SHA-256 du fichier entier est vérifiée côté Java au téléchargement (WFS-306).
- RG-06 : **secours** : la Ville construite par le code (`ville.cpp`, `archi_carte.cpp`) reste dans l'APK, **inchangée**, et doit rester
  performante (tickets de performance en cours) ; paquet absent ou faux → elle est jouée, une ligne au journal du jeu dit pourquoi. Aucun plantage.
  Les autres cartes se jouent comme aujourd'hui (rien n'est retiré).
- RG-07 : mesures au journal : temps de chargement (construction / paquet, médiane de 5), taille de chaque fichier par format de texture ;
  mémoire ≤ 1 Go au chargement, tampon libéré après envoi à la carte graphique.
- RG-08 : parcours complet : accueil → Ville → course → retour, paquet présent (copié à la main) puis absent (secours) ; preuve au journal.
