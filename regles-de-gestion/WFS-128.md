# WFS-128 — Configuration du jeu par un fichier `configgame.json` (à la racine du projet)
Épic : E0 (chargeur dans `src/core/`, nouveaux fichiers) · accroches E3 / E4 / E5 / E8 (≤ 10 lignes par fichier, annoncées au journal) · Priorité : P2 Haute · Dépend de : — · Taille : 3 jours · Demande de l'utilisateur (`tache utilisateur.md`)

## Besoin
Régler le jeu **sans toucher au code** : un seul fichier `configgame.json` à la racine du dépôt où l'utilisateur (et le PO) change les scores, compteurs, nombre de joueurs, espacements, angles et zoom des caméras, etc. L'agent a **la main pour ajouter toute configuration utile** dans ce fichier.

## Règles de gestion
- RG-01 : fichier **`configgame.json`** à la racine du projet, JSON standard, **toutes les valeurs actuelles du jeu y figurent** (les valeurs écrites dans le fichier = le comportement d'aujourd'hui, donc aucun changement visible au premier chargement).
- RG-02 : le fichier est **copié dans l'APK** à la construction (assets) et lu au démarrage ; **si le fichier ou une clé manque, ou si une valeur est invalide**, le jeu garde la valeur par défaut du code et l'écrit au journal (« config : clé X invalide, défaut conservé ») : **jamais de plantage**.
- RG-03 : **surcharge sans reconstruire** : un fichier `configgame.json` placé dans le dossier de données de l'application sur le téléphone (`Android/data/com.waforspeed.game/files/`) **remplace** celui de l'APK ; sur le banc PC, rechargement à chaud à chaque course. Le journal indique quel fichier est utilisé.
- RG-04 : chaque valeur est **bornée** (min / max documentés) ; hors bornes = défaut + avertissement.
- RG-05 : chargeur **maison, sans bibliothèque tierce** (petit lecteur JSON dans `src/core/configgame.*`), avec tests CPU (fichier valide, clé manquante, type faux, hors bornes, JSON cassé).
- RG-06 : **sections minimum**, avec les valeurs actuelles du jeu :
  - `score` : points par 100 m (`floor(dist×0,006)×5`), points par quasi-contact (250), combos et temps de combo, bonus ;
  - `checkpoint` : temps de départ (60 s), temps ajouté par checkpoint (30 s), distance entre checkpoints (600 m) ;
  - `nitro` : consommation, recharge, multiplicateur de vitesse ;
  - `course5` : nombre d'ordinateurs (4), distances proposées (2, 4, 6, 10 km), difficulté, voitures aléatoires (oui / non) ;
  - `joueurs` : nombre maximal de joueurs du duel (4) ;
  - `poursuite` : score de départ (100), distance (10 km), points perdus (trafic −5, glissière −3, police −10, proximité −1 par s), renfort tous les 2 km, nombre de voitures de police, densité des embouteillages, surprises actives ;
  - `trafic` : densité par carte, **espaces / distances de sécurité** entre voitures, vitesses min et max, changements de file ;
  - `camera` : pour chaque vue (poursuite, proche, capot, cockpit) la **distance, la hauteur, l'angle d'élévation, le point visé (avance, hauteur), le champ de vision (zoom)**, l'élargissement avec la vitesse, la secousse ;
  - `commandes` : taille des boutons (dp), sensibilité et zone morte du gyroscope, mode de direction par défaut ;
  - `conduite` : braquage max, adhérence, marche arrière max (valeurs de `Phys` / `player`) ;
  - `qualite` : échelle de rendu, planchers de la résolution dynamique, qualité par défaut ;
  - `duel` : distances proposées, fréquence d'envoi, délai de reconnexion.
- RG-07 : **l'agent ajoute toute autre valeur utile** qu'il trouve en dur dans le code (temps, seuils, tailles, couleurs de score…) en les nommant clairement ; chaque nouvelle clé est ajoutée au fichier **et** au document d'aide.
- RG-08 : **`configgame.README.md`** (ou section du fichier d'aide) : une ligne par clé (sens, unité, min / max, défaut), écrite pour l'utilisateur.
- RG-09 : le code lit la configuration par un accès central (`config().camera.poursuite.distance`…), **pas de lecture de fichier dans les boucles de jeu** ; valeurs mises en cache.
- RG-10 : une ligne de journal au démarrage : fichier utilisé, nombre de clés lues, nombre de valeurs par défaut.
- RG-11 : on veut que ça marche : **d'abord** le chargeur + les sections `score`, `checkpoint`, `course5`, `poursuite`, `camera`, `commandes` branchées ; **ensuite** le reste, par morceaux, sur la même branche, **une seule CI**.
- RG-12 : **gel iOS** : rien d'iOS. Cohérence avec les tickets en cours (WFS-105 caméras, WFS-108 commandes, WFS-110 / 111 modes) : lire leurs constantes **après leur fusion** ou se synchroniser avec `main`.

## À réutiliser
Rien dans le jeu web (constantes en dur dans `js/core/config.js`, `PHYS`, `CAM_MODES`, `DUEL_KMS`) : s'en servir pour retrouver les valeurs d'origine à écrire dans le fichier.

## Critères d'acceptation
- [ ] test CPU du chargeur (valide, manquant, faux type, hors bornes, JSON cassé : aucun plantage)
- [ ] changer `camera.poursuite.angle` / `zoom` et `checkpoint.depart` dans le fichier change le jeu sans modifier le code (captures du banc)
- [ ] fichier absent = comportement identique à aujourd'hui (banc `0 écart(s)`)
- [ ] README des clés complet
