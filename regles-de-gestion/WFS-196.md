# WFS-196 — [CI] Statuts automatiques : 🟣 Fusionné → ✅ Terminé dès que la CI de `main` est verte
Épic : E7 · Priorité : P1 Urgent · Dépend de : WFS-185 🟣 (bloc `on:` de `build.yml`) · Origine : demande de l'utilisateur du 2026-11-06 (« automatiser les statuts des tickets après que la CI termine »)

## Besoin
Aujourd'hui un agent doit venir passer son ticket de 🟣 à ✅ à la main, avec le numéro du run vert de `main` (`CLAUDE.md`). C'est oublié ou mal
écrit (WFS-109, WFS-134 restés « En cours » ; WFS-150 resté 🟣). Un robot le fait à la fin de chaque run de `main`.

## Règles de gestion
- RG-01 : nouveau workflow `.github/workflows/statuts.yml`, déclenché par `workflow_run` (`workflows: [build.yml]`, `types: [completed]`,
  `branches: [main]`) ; `permissions: contents: write` seulement ; `concurrency` d'un seul run à la fois, sans annuler celui en cours.
- RG-02 : **run tout vert** (`conclusion == success`, tous les jobs verts ou sautés par conception) : pour chaque ligne du tableau de
  `TACHES.md` dont la case **Statut** commence par 🟣, retrouver le commit de fusion (PR `#NNN` de la ligne ou de son titre de commit
  `(#NNN)`, sinon hash cité) ; s'il est ancêtre du commit du run (`git merge-base --is-ancestor`), remplacer **la case Statut seulement** par
  `✅ Terminé (CI main #<run_number>)`. Même chose pour la ligne de détail `**WFS-XX — …**` et, s'il y en a une, la case « État » de l'agent dans `track-agent.md`.
- RG-03 : **run rouge** : aucun statut ne change ; une entrée au journal : run, job(s) en échec, tickets 🟣 contenus dans ce run.
  Run **annulé** : rien (le run suivant tranchera).
- RG-04 : **ne jamais deviner** : ligne mal formée (nombre de colonnes, statut dans la mauvaise case), PR introuvable ou commit absent → la ligne
  reste telle quelle et elle est listée au journal « à corriger par le PO ».
- RG-05 : une entrée au journal par run traité : `### <date -u à la seconde> — Statuts automatiques, CI main #N (robot statuts)`, avec la liste
  des tickets passés en ✅.
- RG-06 : le robot ne modifie que `TACHES.md`, `track-agent.md` et `journal.md`, puis fait **un** commit sur `main` dont le titre finit par
  `(robot statuts)` (règle des commits) ; s'il croise un autre envoi : `git pull --rebase` puis nouvel essai, 5 fois au plus. Ces fichiers
  `.md` sont dans `paths-ignore` de `build.yml` : le commit du robot ne relance pas la CI (à vérifier, critère ci-dessous).
- RG-07 : le script est dans `tools/qa/statuts.py` (Python 3 de la bibliothèque standard, aucune dépendance), avec un test
  `tools/qa/test_statuts.py` sur un `TACHES.md` d'exemple : ligne 🟣 contenue dans le run → ✅ ; non contenue → inchangée ; ligne mal formée →
  inchangée et listée ; run rouge → rien.
- RG-08 : `CLAUDE.md` (ligne « Statuts et CI ») est complété par le PO à la fusion : le ✅ est posé par le robot, l'agent garde le 🟣 et la
  correction immédiate si c'est rouge à cause de lui.

## Zone de code
E7 : `.github/workflows/statuts.yml` (nouveau), `tools/qa/statuts.py`, `tools/qa/test_statuts.py`. Interdit : `build.yml` (bloc `on:` de WFS-185),
tout autre fichier de code, iOS (gel). Si le dépôt refuse l'envoi direct du robot sur `main` (protection de branche), le noter au journal et
poser **une** question à l'utilisateur dans `tache utilisateur.md` (réglage GitHub à autoriser).

## Critères d'acceptation
- [ ] tests de `tools/qa/test_statuts.py` verts en local (4 cas de RG-07)
- [ ] sur `main`, au premier run vert après la fusion : les tickets 🟣 contenus passent ✅ avec le numéro du run, commit `(robot statuts)`, entrée au journal
- [ ] le commit du robot ne déclenche aucun run de `build.yml`
- [ ] un run rouge ne change aucun statut et laisse une entrée au journal
- [ ] ligne `qa/Check.md` ; statut 🟣 puis ✅ (posé par le robot lui-même)
