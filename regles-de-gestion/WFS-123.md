# WFS-123 — Tenue sur téléphone : chauffe, batterie et 60 images/s stables
Épic : E7 · Priorité : P2 Haute · Dépend de : WFS-15 ✅, WFS-86 ✅, WFS-104 ✅ (qualité automatique), WFS-29 ✅ (JeuActivity)

## Besoin (qui, quoi, pourquoi)
Le joueur teste l'APK sur son propre téléphone, pendant de longues sessions (poursuite de 10 km, course à 5, duel).
Aujourd'hui le jeu ne tient aucun compte de la **chauffe** du téléphone : quand Android bride le processeur, les
images/s s'effondrent d'un coup et la batterie fond. Sur les écrans 90 / 120 Hz, la synchro FIFO peut aussi viser
une fréquence que le GPU ne tient pas (saccades). Objectif : une course fluide qui **reste** fluide après 15 minutes,
sans que le joueur ait à toucher aux réglages.

## Règles de gestion
- RG-01 : **État thermique d'Android** lu par le NDK (`android/thermal.h`, `AThermal_acquireManager`,
  `AThermal_registerThermalStatusListener`, API 30+ ; chargé par `dlsym` pour garder `minSdk 26`, rien sous API 30).
  Nouveau fichier `src/platform/chauffe_android.cpp` + `src/platform/chauffe.h` : `int chauffeNiveau()` (0 = aucune,
  1 = légère/modérée, 2 = sévère ou plus) lu par la boucle de jeu, jamais par le thread du capteur.
- RG-02 : **Chauffe sévère (niveau 2) en course** → rétrogradation d'**un** niveau de qualité (Haute → Moyenne →
  Basse), une seule fois par course, **même si le joueur a choisi sa qualité** (la chauffe passe avant) ; bandeau du
  jeu web « Graphismes rapides — pour plus de fluidité » (déjà dans `qualite_systeme.cpp`, réutilisé tel quel). Le
  niveau choisi par le joueur est **rétabli** au menu quand la chauffe est retombée à 0 depuis 60 s (pas d'écriture
  dans la sauvegarde : la rétrogradation de chauffe n'est jamais enregistrée).
- RG-03 : **Chauffe modérée (niveau 1)** → la résolution dynamique (`qualite::Auto::echelle`) ne remonte plus
  (aucun +0,1), sans rien couper d'autre.
- RG-04 : **Fréquence d'affichage** : `ANativeWindow_setFrameRate(fenêtre, 60, …)` (API 30+, par `dlsym`) à chaque
  création de la fenêtre, pour que les écrans 90 / 120 Hz affichent 60 images/s stables (FIFO conservé, `vk.cpp`
  inchangé). Rien en dessous d'API 30.
- RG-05 : **Mode performances soutenues** : `Window.setSustainedPerformanceMode(true)` dans `JeuActivity`
  (`onResume`, si `PowerManager.isSustainedPerformanceModeSupported()`), coupé en `onPause`.
- RG-06 : **Hors course** (menus, garage, terrain, pause) : plafond de **30 images/s** (attente de la boucle
  `android_main`, pas de changement Vulkan) pour économiser la batterie ; 60 images/s dès l'écran Course / décompte.
- RG-07 : **Journal** : `CHAUFFE niveau=N (statut Android S)` à chaque changement, `CHAUFFE rétrogradation Haute →
  Moyenne`, `CHAUFFE rétabli Haute`, `IPS plafond 30 / 60`. Rien de plus (pas de spam : une ligne par changement).
- RG-08 : **Banc PC** : variable `WFS_CHAUFFE=0|1|2` (et `WFS_CHAUFFE_APRES=<s>`) dans `desktop_main.cpp` simule
  l'état thermique (implémentation bureau de `chauffeNiveau()`), pour prouver RG-02 / RG-03 / RG-06 sans téléphone.
- RG-09 : **Test CPU** `tests/test_chauffe.cpp` (logique pure, sans Vulkan) : niveau 2 → une seule rétrogradation par
  course ; choix du joueur rétrogradé puis rétabli après 60 s à 0 ; niveau 1 → échelle bloquée ; plafond 30 / 60
  selon l'écran.
- RG-10 : **Parcours complet** (principe n° 1 du PO), prouvé au journal du banc avec `WFS_CHAUFFE=2 WFS_CHAUFFE_APRES=5` :
  accueil → Course solo → Checkpoint → Continuer → garage → Choisir → terrain → Rouler → course (rétrogradation +
  bandeau à ≈ 5 s) → fin → Menu → accueil (plafond 30) ; puis `WFS_CHAUFFE=0` : qualité choisie rétablie. « 0 écart(s) OK ».
