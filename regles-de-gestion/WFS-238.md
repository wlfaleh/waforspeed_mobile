# WFS-238 — [TECHNIQUE] Notification en temps réel à chaque APK de main publié (commentaire dans une issue GitHub épinglée)
Épic : E7 · Priorité : P1 Urgent · Dépend de : — · Origine : demande de l'utilisateur à l'agent expert ci (2026-11-07, « une notification pour chaque
fichier APK disponible », en temps réel ; contrôle toutes les heures refusé) ; solution proposée par l'agent expert ci ; créé par le PO le 2026-11-07 13:25 UTC.

## Besoin (qui, quoi, pourquoi)
L'utilisateur teste lui-même l'APK de `main` sur son téléphone. Il veut être prévenu **à la seconde** où un nouvel APK est en ligne, sans aller vérifier.
L'application GitHub du téléphone envoie une notification à chaque mention `@wlfaleh` : un commentaire par APK publié suffit, sans service extérieur ni secret.

## Règles de gestion
- RG-01 : à la **fin du job `publication-apk`** de `.github/workflows/build.yml`, une étape ajoute **un commentaire** dans une issue GitHub fixe
  **« 📱 Nouvel APK de main »** du dépôt `wlfaleh/waforspeed_mobile`.
- RG-02 : **seulement sur `main`** (`github.ref == 'refs/heads/main'`) et **seulement si l'APK a bien été publié** (étape de publication réussie,
  `if: success()`). Aucun commentaire pour une branche, un lancement à la main sur une branche, un run de nuit ni une publication en échec.
- RG-03 : **un commentaire par APK publié**, jamais deux pour le même run (pas de nouvel essai qui doublonne).
- RG-04 : contenu du commentaire : mention **`@wlfaleh`** (c'est elle qui déclenche la notification), **numéro de construction** (`github.run_number`),
  **commit court** (7 caractères), **tickets WFS-XX** du run (lus dans les messages des commits de l'envoi ; réutiliser au besoin la liste du job `résumé`,
  WFS-237 ; si elle ne se lit pas : « tickets : voir le résumé du run » et le lien du run), **lien fixe de l'APK**
  https://github.com/wlfaleh/waforspeed_mobile/releases/download/apercu/WaForSpeed.apk, lien du run. Texte en français, court (≤ 8 lignes).
- RG-05 : l'issue est **créée une seule fois** puis **épinglée** ; elle est retrouvée par son titre exact (ou par une étiquette dédiée) ; si elle n'existe
  pas, l'étape la crée (une seule, jamais une issue par APK). Son numéro est noté dans `pipeline.md`.
- RG-06 : jeton **`GITHUB_TOKEN`** seulement, permission **`issues: write`** déclarée **au niveau du job** `publication-apk` (les autres jobs ne changent pas
  de permissions). Aucun secret ajouté, **aucun envoi hors de GitHub** (`regles-reseau.md` respecté : pas de webhook, pas de service de notification extérieur).
- RG-07 : **échec non bloquant** : un échec du commentaire donne un `::warning::`, l'étape finit verte (`continue-on-error: true` ou `|| echo ::warning::`),
  jamais un job rouge ; l'étape vient **après** la publication et ne la retarde pas (délai court, `timeout-minutes: 2` sur l'étape).
- RG-08 : **aucun** banc, test, seuil ni job affaibli, retiré ou sauté ; la publication de l'APK (`tools/qa/publier_apercu.sh`) garde son comportement ;
  aucun code fusionné retiré.
- RG-09 : `.claude/skills/expert-ci/references/pipeline.md` mis à jour (étape de notification, issue utilisée, permission, comportement en échec).
- RG-10 : US technique : CI de la branche permise (`workflow_dispatch` de `build.yml`, branche synchronisée avec `main`) autant de fois que nécessaire,
  **une à la fois**, chaque lancement noté au journal (numéro du run, ce qu'il vérifie). Sur une branche, l'étape doit être **sautée** (preuve de RG-02).

## À réutiliser (dans ce dépôt)
- Le job `publication-apk` (`build.yml`, WFS-87, WFS-106, WFS-185) et son `GH_TOKEN` : on ajoute une étape, on ne le recrée pas.
- La liste des tickets du job `résumé` (WFS-237) si elle est accessible ; `gh` est présent sur les lanceurs (`gh issue list / create / comment`, `gh api` pour épingler).

## Critères d'acceptation
- [ ] Après une fusion sur `main`, dès que l'APK est publié, un commentaire apparaît dans l'issue épinglée « 📱 Nouvel APK de main » avec `@wlfaleh`,
      le numéro de construction, le commit court, les tickets et le lien de l'APK ; l'utilisateur reçoit la notification sur son téléphone.
- [ ] Un seul commentaire par APK publié ; aucune issue en double.
- [ ] CI de branche : l'étape est sautée (aucun commentaire) ; le job `publication-apk` reste vert.
- [ ] Un échec du commentaire (essayé ou raisonné) ne rend pas le job rouge et ne retarde pas l'APK.
- [ ] `pipeline.md` à jour.

## Hors périmètre
Notification des captures, du banc de nuit ou des runs rouges ; service extérieur (courriel, Slack, ntfy…) ; changement de la publication de l'APK.
